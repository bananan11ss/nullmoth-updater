# Исправления поверх драйвера 2.0.0

Эта папка — исходники официального релиза **v2.0.0** (тег `bb53f0a809`) с исправлениями. Все изменения в одном
файле: `FIXES.patch`. Готовый плагин: `out/NVMTLDriver` (release-сборка, x86_64, подпись ad-hoc).

## Что проверено, а что нет

| Часть | Собрано | Проверено на твоей RTX 4070 Laptop |
|---|---|---|
| Metal-плагин (`plugin/`) | да, 0 ошибок, те же 332 предупреждения, что у оригинала | да, тестовый стенд `tools/run_harness.sh` (плагин грузится в отдельный процесс, в систему ничего не ставится) |
| Скрипты установки (`package/`, `app/Resources/`) | `bash -n` без ошибок | нет, на реальной установке не запускались |

не дать системе загрузиться.

### Новое: настройки для одной программы

Release-плагин удаляет из окружения все `NVMTL_*`/`NVK_*`/`NVRM_*`, поэтому настроить отдельную игру раньше
было нельзя: только весь `nvrm610.conf` целиком, вместе с WindowServer. Теперь строка

```
java:NVMTL_SHARED_VRAM=1
```

действует только на процесс `java` (Minecraft) и перекрывает общую строку с тем же ключом. Старые плагины и
Vulkan-драйвер такие строки пропускают. Это включает вкладка «Игры и производительность» в NullMoth Updater.

### Загрузка текстур без ожидания (для Minecraft)

Профиль Minecraft на этой машине (`sample`, 8 с): около 23% времени потока рендера уходило в
`glTexSubImage2D → replaceRegion → nvmtl_vk_submit_wait`. Каждое обновление текстуры отправлялось на GPU
отдельно, и процессор ждал, пока GPU доделает **всю** работу, стоявшую перед ним. Чем больше чанков, тем длиннее
очередь, тем дольше каждое ожидание, отсюда и падение FPS с дальностью прорисовки.

В 2.0.0 уже была опция `NVMTL_ASYNC_TEX_UPLOAD=1`, но вторая загрузка в ту же текстуру ждала первую, а
Minecraft пишет десятки спрайтов в один атлас. Теперь все незавершённые загрузки стоят в одной общей очереди
(FIFO), у каждой свой staging-буфер. Порядок копий обеспечивает сама очередь GPU, а каждая новая загрузка
освобождает уже выполненные, не дожидаясь их. Очередь ограничена: не больше 128 загрузок и 256 МБ staging.
Это важно: каждая незавершённая загрузка держит около трёх соединений с ядром, а на процесс их положено 4096.
Первый вариант (цепочки на каждую текстуру) на старте Minecraft, где тысячи текстур пишутся по одному разу,
упирался в этот лимит и падал внутри NVK. Перед чтением, перемещением или удалением текстуры драйвер дожидается
очереди до последней загрузки в неё.

| Тест | Синхронно | Асинхронно |
|---|---|---|
| `texup`: 600 загрузок, 12 промежуточных чтений на GPU, итоговое чтение | 10/10 | 10/10 |
| `texbench`: 60 кадров по ~2 мс GPU + 20 загрузок | 3,7–5,9 мс/кадр | 4,0–4,2 мс/кадр |
| `texlate`: загрузка завершена после 5000 отправок | PASS | оригинал 2.0.0: **FAIL** (GPU отключается); исправленный: PASS |
| `texmany`: 3000 текстур, каждая загружена один раз | PASS | PASS |

Включается строкой `java:NVMTL_ASYNC_TEX_UPLOAD=1` (переключатель в апдейтере).

**Почему Minecraft падал с этой опцией (баг есть и в оригинальной 2.0.0).** Каждую отправку на GPU драйвер
помечает «свидетелем» в кольце на 4096 ячеек. Асинхронная загрузка может ждать завершения, пока её текстуру не
прочитают или не удалят. За это время успевают пройти тысячи отправок, и ячейку свидетеля занимает более поздняя.
Проверка видела чужой номер, считала работу потерянной и **отключала GPU для всего процесса**. Дальше
`GPU event segment submission failed`, «незагружаемые» текстуры и `SIGSEGV` в `AppleMetalOpenGLRenderer`. Тест
`texlate` воспроизводит это на оригинале. Исправление: более поздний свидетель в той же ячейке доказывает, что
наша работа завершена, ведь все отправки идут в одну очередь, а барьер перед записью свидетеля ждёт всё
отправленное раньше.

В последнем замере `texbench` все режимы дают около 4 мс на кадр: тест упирается в GPU. Выигрыш в самом
Minecraft нужно мерить в игре.

### Важно про официальный 2.0.0

Плагин в релизе 2.0.0 собран **без** `RELEASE=1`. В нём включены журнал `nvmtl.log`, FPS-файлы и замеры
проходов, а `build/build_plugin.sh` такую сборку считает ошибкой. Поэтому в 2.0.0 переменные окружения работают,
но каждое Metal-приложение тратит время на журнал. `out/NVMTLDriver` — нормальная release-сборка.

## Скрипты установки

- `/Users/Shared/nvfw` (прошивка GSP, её грузит GPU) был доступен на запись всем пользователям, а файлы
  дописывались поверх старых. Теперь папка пересоздаётся, принадлежит root, и установка отказывается работать
  через символическую ссылку.
- Кэш шейдеров сохранялся после обновления, хотя его ключ не зависит от версии переводчика: игры продолжали брать
  старый результат. Теперь, если плагин, переводчик или `air-opt` изменились, кэш начинается заново.
- Приложение 1401 создавало `/Library/NullMoth` с правами 0700 (`umask 077`), поэтому не могло прочитать
  `driver-version` и бесконечно предлагало обновиться. Теперь права 0755, а файлы внутри сохраняют свои права.
- Сообщение `Undo: sudo ./uninstall.sh <backup>` обещало откат, хотя `uninstall.sh` просто удаляет драйвер.
  Текст исправлен.

## Как повторить тесты

```bash
cd fixed-2.0.0 && tools/run_harness.sh out/NVMTLDriver
```

Для сборки плагина нужны заголовки Vulkan (`git clone --branch v1.4.328 https://github.com/KhronosGroup/Vulkan-Headers`):

```bash
cd plugin && xcrun clang -arch x86_64 -bundle -fobjc-arc -O1 -DNVMTL_RELEASE=1 -Wno-protocol \
  -Wno-incomplete-implementation -I<Vulkan-Headers>/include -o ../out/NVMTLDriver NVMTLDevice.m \
  -framework Foundation -framework Metal -framework IOSurface -framework IOKit
```

По правилам репозитория (`AGENTS.md`, `CONTRIBUTING.md`) pull request'ы, написанные ИИ, закрываются без
рассмотрения. Если хочешь отправить что-то из этого автору, разберись в изменении и напиши его сам.
